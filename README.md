# 珠三角房产智能问答（RAG）

拿广深佛莞惠五个城市的二手房数据做了个检索问答系统。用户用自然语言提问，系统先抽结构化条件过滤，再做混合检索加重排，最后交给大模型生成推荐。

## 为什么做这个

房产检索有个别扭的地方：用户问"深圳南山 500 万以下的三房"，这里面**"500 万以下"是硬约束，不是语义相关性问题**。如果直接拿语义检索去匹配，会召回一堆"讲得挺像但价格超标"的房子。

所以链路的第一段不是向量检索，是**结构化过滤**。先用正则把城市、区域、价格、户型、面积抽出来，把候选集从一万五千多条砍到几十到几百条，再检索。

第二段是**混合检索**。为什么不能只用向量：

- 向量对**专有名词**很弱。"天健和郡府"和"附近某个小区"在向量空间里几乎没区别，但 BM25 用 jieba 分词后能精确命中。
- 反过来，用户说"地铁房""近学校"，**没有共同词但语义相关**，BM25 完全无能为力。

两路是互补的，不是冗余的。

第三段是 **Cross-Encoder 重排**。双塔模型是 query 和 doc 各自编码再算相似度，快但建模不了细粒度交互；交叉编码器把两者拼在一起过模型，慢但准。所以用双塔召回、交叉编码器精排，先便宜地筛出小集合，再贵地精确排序。

最后才把 Top-K 拼进 prompt 交给 DeepSeek 生成，prompt 里明确写了"房源信息不足就如实告知，不要编造"。

## 数据

四个来源合并：房天下二手（10945）、58 同城二手（2036）、房天下成交（1878）、房天下新房（208），清洗后 **15067 行 × 10 列**。字段：城市、区域、户型、总价、面积、单价、小区名称、爬取时间、朝向、数据来源。

**但四个来源的完整度差很多**，这直接影响能按什么条件筛：

| 字段 | 为空/0 的行数 | 占比 |
|---|---|---|
| 总价 | 450 | 3.0% |
| 面积 | 7841 | **52.0%** |
| 单价 | 8213 | **54.5%** |

原因主要在房天下二手那 10945 条里，**约 7797 条只有总价，没有面积和单价**（源头页面就没给）。新房那边相反，只有均价没有总价，总价是用 `单价 × 面积 / 10000` 反推的，属于有损推算。

所以：**按"总价"筛选是可靠的（97% 可用），按"面积/单价"筛选就只剩一半数据。** 这个差异是真实的，不是清洗失误。

> **数据没有提交到仓库**（`.gitignore` 排除了 `1_data/` 下的数据和向量库），所以 clone 下来**跑不起来**，需要自己准备数据，向量库也要重建（当前 15063 条向量）。

## 做过什么改进、还剩什么问题

### 已修复

**融合方式改成了 RRF 按排名融合。** 原来是 `alpha * BM25 + (1-alpha) * 向量相似度`，问题在于 BM25 归一到 0-1、余弦值域是 -1~1，两个量纲不同的分数直接线性加权，alpha 没有明确含义，换一批数据最优值就会漂移。现在改成

```
score(d) = alpha * 1/(k + rank_bm25(d)) + (1-alpha) * 1/(k + rank_vector(d))
```

只用排名、对量纲免疫，k=60（经验平滑值），alpha 的含义变成"两路权重"（0.5 即等权）。实测收益不只是"更正确"：`广州天河区500万以下` 这类查询，修之前非结构化路径会返回佛山顺德的房源，修之后返回的才是天河区。

**向量库现在真正承担职责了（已修）。** 原来 `get_collection()` 初始化了 collection 却从没被查过，向量是在 DataFrame 上暴力算的。**注意我并没有改成 `collection.query()`**，实测数据不支持那么做：

| 候选集规模 | 候选集精确余弦 | `collection.query()` (ANN) | 两者 top20 交集 |
|---|---|---|---|
| 45 条 | 66 ms | 163 ms | 10/20 |
| 878 条 | 625 ms | 165 ms | **0/20** |
| 1101 条 | 986 ms | 170 ms | 6/20 |

**这张表的读法要小心**：两者不一致不是因为 ANN 差，而是因为**我的结构化过滤在 pandas 层做，没有下推给向量库**。`query()` 只能返回全库全局近邻，不知道价格/区域这些约束，求交自然大量落空。要让 ANN 有意义，得把过滤条件写进 metadata 用 `where` 下推，那需要改入库时的 metadata 结构。

不过**在当前规模下即使下推也没必要**（见下）。而真正的瓶颈是原先每次查询都要重新编码候选集（600~900ms 全花在这上面）。

所以改成：**初始化时用 `collection.get(include=['embeddings'])` 把向量一次性读进内存缓存**（476ms、22.1MB、库里的向量本来就归一化过、范数实测为 1），之后任意查询的余弦退化成一次矩阵乘法（全库 15063×384 只要 0.6ms）。向量库由此成为向量的**事实来源**，而检索仍是精确的。

**每次查询都在重建（已修）。** `Reranker()` 原来在 `search()` 里当场实例化，等于每个查询重新加载一遍 Cross-Encoder；现在缓存为实例属性。加上向量缓存，**端到端自检耗时从 53s 降到 18.2s，单查询平均从 600~900ms 降到 114ms。**

**依赖清单已从 243 包裁到 12 个（已修）。** 原来那份是整个虚拟环境的转储（含 jupyter、scrapy、playwright、pyinstaller、kubernetes）。现在按"代码里真实 import 的直接依赖"重列，并注明刻意排除的东西。

**价格清洗的单位假设曾经是错的（已修）。** 原 `clean_price()` 的注释说"带'万'就直接取数字，否则按万元处理"，但代码里没判断"万"字，实测输入 `3500000`（元）会被 `min(price, 9999)` 截断成 9999 万。已补上单位分支。**教训是保护性逻辑要和它依赖的假设一起审。**

**`load_to_chromadb_origin.py` 是个危险的历史脚本（已加守卫）。** 它没有 `__main__` 保护，**光是 `import` 就会删掉正式集合并重新写库**（实际误伤过一次，把 15063 条覆盖成 6902 条）；而且它用 uuid 当 id，与检索侧"id = dataframe 行号"的约定不兼容，用它建的库会让向量分量全部取不到向量。现在代码已包进 `main()`，导入零副作用，并在文件头标注废弃。**重建向量库请用 `load_to_chromadb.py`。**

**凭据曾经写死在源码里（已修）。** `3_api/config.py` 的 MySQL 配置是从早期爬虫项目直接复用过来的，带着明文口令。这套配置现在没被主流程使用，但凭据不该出现在源码里，已改成从环境变量读取。

顺带说一句：`.env` 里的 DeepSeek key、钉钉密钥这些一直用 `.gitignore` 挡着，**没有进过版本库**。

### 还没做

**ETL 的异常值处理仍是覆写而不是标记。** 原 ETL 把偏离区域中位数 50% 以上的单价直接改成中位数，真实离群信息就永久丢了。应改为打标记、保留原值。

**Docker 构建仍跑不通。** `COPY 1_data/cleaned_data/` 这个写法会去找 `cleaned_data/cleaned_data`；Python 侧路径已改成由 `__file__` 推导，但 Dockerfile 本身还没动。依赖清单已从 243 裁到 12，镜像体积问题基本解决，剩 COPY 写法与工作目录要重写。

**评估缺检索侧指标。** 见下一节。

## 评估

用 DeepSeek 做 RAGAS 风格的打分，5 个测试问题，忠实度 **0.76**、相关性 **0.49**。

**这两个数字怎么解读比数字本身重要**：忠实度高、相关性低，通常意味着"回答忠实于检索结果，但检索结果本身不够相关"，也就是**问题出在检索层，不是生成层**。

而我的评估**只做了端到端一层，没有检索侧指标**（召回率@K、MRR、NDCG），所以**定位不到故障出在哪一层**。这是目前最大的缺口。

另外这套评估还有两个方法问题：judge 用的是生成答案的同一个模型（DeepSeek），存在自偏好；样本只有 5 条，而且解析失败时兜底返回 0.5，会污染均值。
