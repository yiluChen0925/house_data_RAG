# 珠三角房产智能问答（RAG）

拿广深佛莞惠五个城市的二手房数据做了个检索问答系统。用户用自然语言提问，系统先抽结构化条件过滤，再做混合检索加重排，最后交给大模型生成推荐。

## 为什么做这个

房产检索有个别扭的地方：用户问"深圳南山 500 万以下的三房"，这里面**"500 万以下"是硬约束，不是语义相关性问题**。如果直接拿语义检索去匹配，会召回一堆"讲得挺像但价格超标"的房子。

所以链路的第一段不是向量检索，是**结构化过滤**——先用正则把城市、区域、价格、户型、面积抽出来，把候选集从近八千条砍到几十到几百条，再检索。

第二段是**混合检索**。为什么不能只用向量：

- 向量对**专有名词**很弱。"天健和郡府"和"附近某个小区"在向量空间里几乎没区别，但 BM25 用 jieba 分词后能精确命中。
- 反过来，用户说"地铁房""近学校"，**没有共同词但语义相关**，BM25 完全无能为力。

两路是互补的，不是冗余的。

第三段是 **Cross-Encoder 重排**。双塔模型是 query 和 doc 各自编码再算相似度，快但建模不了细粒度交互；交叉编码器把两者拼在一起过模型，慢但准。所以用双塔召回、交叉编码器精排——先便宜地筛出小集合，再贵地精确排序。

最后才把 Top-K 拼进 prompt 交给 DeepSeek 生成，prompt 里明确写了"房源信息不足就如实告知，不要编造"。

## 数据

**其中 1587 行总价为空或 0**，所以价格类筛选实际可用 **6393 行**。这个比例不低，清洗时没处理掉——算是个遗留问题。

## 已知问题

**文档写的融合方式和代码不一致。** README 之前写的是"RRF 融合"，代码实际是 `alpha * BM25 + (1-alpha) * 向量相似度` 的加权求和。而且这个写法**本身有问题**：BM25 我归一化到了 0-1，余弦相似度的值域是 -1 到 1，两个量纲不同的分数直接线性加权，那个 alpha 是没有意义的。RRF 存在的理由就是它按排名融合、对量纲免疫——所以正确做法是改成按排名融合，而不是把 README 改回去。

**ChromaDB 装了但没真正用起来。** 代码里 `get_collection()` 初始化了 collection，但检索实际是在 pandas DataFrame 上暴力算余弦（整个项目没有一处 `collection.query()`）。候选集本来就被结构化过滤到几十条了，ANN 索引的收益接近零——但这个取舍该说清楚，而不是留一段没用上的代码。

**每次查询都在重建。** `search()` 里每次都重建 `BM25Okapi`、重算全部候选向量，而且 `Reranker()` 是当场实例化——等于每次查询重新加载一遍 Cross-Encoder。这个应该缓存成模块级。

**价格清洗的单位假设是错的。** `clean_price()` 的注释写"带'万'就直接取数字，否则按万元处理"，但代码里**根本没判断"万"字**。实测：输入 `3500000`（元）会被 `min(price, 9999)` 截断成 **9999 万**。那个 `min` 本意是防录入错误，但在"单位是元"的假设下它变成了数据污染的元凶。教训是保护逻辑要和它依赖的假设一起审。

**异常值被覆写而不是标记。** ETL 里把偏离区域中位数 50% 以上的单价直接改成中位数，真实的离群信息就永久丢了。应该打标记、保留原值。

**MySQL 密码写死在源码里。** `3_api/config.py` 里 `password: "123456"`。这个文件其实是死代码（里面的路径配置和实际目录结构对不上），但凭据不该出现在源码里。顺带说一句，`.env` 里的 DeepSeek key、钉钉密钥这些我是用 `.gitignore` 挡住的，**没有进过版本库**。

**Docker 构建目前跑不通。** `COPY 1_data/cleaned_data/` 这个写法会去找 `cleaned_data/cleaned_data`；代码里还有一堆 Windows 绝对路径；`requirements.txt` 是整个虚拟环境的转储（243 个包，含 torch、jupyter、scrapy 这些无关的），镜像会很大。真要部署得先把依赖裁一遍、路径改成环境变量。

## 评估

用 DeepSeek 做 RAGAS 风格的打分，5 个测试问题，忠实度 **0.76**、相关性 **0.49**。

**这两个数字怎么解读比数字本身重要**：忠实度高、相关性低，通常意味着"回答忠实于检索结果，但检索结果本身不够相关"——**问题出在检索层，不是生成层**。

而我的评估**只做了端到端一层，没有检索侧指标**（召回率@K、MRR、NDCG），所以**定位不到故障出在哪一层**。这是目前最大的缺口。

另外这套评估还有两个方法问题：judge 用的是生成答案的同一个模型（DeepSeek），存在自偏好；样本只有 5 条，而且解析失败时兜底返回 0.5，会污染均值。

## 怎么跑

